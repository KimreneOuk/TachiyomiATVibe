## Findings

1. **F-1 HIGH — nested bucket-1 admission makes analysis categorically non-functional with real engines (blocks FF-01 activation).**
   `translator/analysis/AnalysisChunkExecutor.kt:163-171` wraps each transport call in `withTranslationRetry(requestMetadata = metadata, governor = SharedProviderRequestGovernor.instance)`; with non-null `requestMetadata` the retry driver itself admits via `governor.executeValue` (`retry/TranslationRetry.kt:196-201`). The real transports then admit a second time on the SAME normalized key (backend/model/credentialScope): `translator/providers/OpenAiCompatibleTranslator.kt:143` and `translator/providers/GeminiTranslator.kt:201`. Default policy `maxInFlight = 1` (`translator/ProviderRequestGovernor.kt:70`); the inner admission sees `inFlight >= maxInFlight` (`:465`), polls until `maxForegroundWaitMs` (15 s, `waitOrDefer :484-502`), then defers — `ProviderRequestPausedException` (QUOTA_EXHAUSTED/PAUSE) → `TransportPaused` → `AnalysisChunkRunOutcome.Paused`. Scenario: enable FF-01 with Gemini → first analysis chunk hangs 15 s, run pauses typed; resume repeats forever; profile never freezes; pipeline dead-ends. It is the only `requestMetadata`-passing caller in main; all other paths (including the translation envelope at `pipeline/batch/ProfileEnvelopeExecutor.kt:564-565`) admit exactly once inside the transport. Secondary: the outer `executeValue` also consumes a root `RequestRetryBudget` attempt, so attempts double-count. Tests miss it because `AnalysisEngineTransportTest` and the executor tests use fakes that never self-admit.
   **RESOLUTION: FIXED — commit `45216e7` (2026-09-07).** The executor no longer holds a governor and passes no `requestMetadata` to the retry driver; the transport makes the single admission (the translation-envelope idiom). Pinned by a self-admitting-transport regression test on a real `maxInFlight=1` governor (`AnalysisChunkValidationTest` — old code returns TransportPaused via `ProviderRequestPausedException`, new code Validated).

2. **F-2 MED — ST-14 resume clause violated: no FINALIZE-resume branch; a crash between FINALIZE and COMPLETE re-runs the whole machine.**
   `pipeline/batch/ChapterProfileBatchCoordinator.kt:240-253` reuses only the runId, then `:284` unconditionally publishes a fresh RUN_SNAPSHOT record. A process death after the FINALIZE record (`:1475`) but before COMPLETE (`:1544`) resumes by moving the durable state backward (FINALIZE → RUN_SNAPSHOT) and re-entering OCR/TRANSLATE — the contract forbids re-entering TRANSLATE from FINALIZE. Converges safely only because every commit is CAS-fenced and profile reuse short-circuits paid work; still a state-machine regression plus duplicate phase records. Fix: on entry, a prior record in FINALIZE/COMPLETE should jump straight to the finalize/idempotent-completion path.
   **RESOLUTION: FIXED — commit `9baa8aa` (2026-09-05).** `resumeFinalizeOrComplete` gates dispatch entry: a durable FINALIZE record re-enters the idempotent `drainFinalizeAndComplete` (committed pages skip; COMPLETE stays the run's FIRST/ONLY closure record; fingerprint/digest mismatch per ST-15 starts a fresh run); a durable COMPLETE under flag ON resumes as a zero-work finished outcome (`RESUME_COMPLETE_REASON`). Enabling discovery: the FINALIZE record had been SILENTLY REJECTED on every run — D6's executor counters pushed phaseCounters past the 32-key bound; `publishRecord` now trims the oldest keys so the phase transition always lands. Pinned by `Stage7FinalizeResumeCoordinatorTest` (2 tests: FINALIZE resume reaches COMPLETE with zero OCR/analysis/translate; COMPLETE resume byte-identical, zero work).

3. **F-3 MED — `COMPLETED` is returned even when the COMPLETE record was durably rejected.**
   `publishRecord` (`ChapterProfileBatchCoordinator.kt:2339-2362`) treats rejection as log-only WARN, and `runFinalizeAndComplete` then unconditionally returns `BatchPass1Status.COMPLETED` (`:1560-1568` region). A phaseCounters cap rejection or a lost whole-manifest CAS (reader-origin write racing finalize) leaves the durable record at TRANSLATE/FINALIZE while the queue/tracker is told COMPLETED — the exact class of silent failure the wave-7b counter fix was meant to remove. Fix: propagate the COMPLETE publication outcome into the returned status (COMPLETED only on `Committed`), and/or retry the publication.
   **RESOLUTION: FIXED — commit `9baa8aa` (2026-09-05).** `publishRecord` now returns `TransactionOutcome?`; the run-closure COMPLETE publication in `drainFinalizeAndComplete` is gated — `Committed` returns COMPLETED as before, anything else returns typed PAUSED with `RUN_CLOSURE_REJECTED_REASON` (the run stays durably at FINALIZE; a later dispatch re-enters the F-2 FINALIZE resume, which re-attempts the closure). Advisory callers are unchanged.

4. **F-4 MED — `TreatAsFinished` is broader than FF-01e.2a and can permanently retire pages that never reached display.**
   `decideResume` (`ChapterProfileBatchCoordinator.kt:2585-2592`) maps any recorded COMPLETE + flag-OFF to TreatAsFinished, consulted on every `runBatchPass1` (`pipeline/batch/BatchChapterTranslator.kt:657-663`). But the T924 COMPLETE fires on translation-committed alone: `t924PageTerminalAtFinalize` (`:1588-1606`) counts translation READY/PARTIAL terminal regardless of inpaint failure. Scenario: a flagged run completes with two pages inpaint-FAILED (committed translations, no rendered display); user flips FF-01 OFF and re-requests translation → typed COMPLETED, legacy schedule never runs → those pages never render and offer no retry. FF-01e.2a authorizes TreatAsFinished only when "final per-page displays committed". Fix: gate TreatAsFinished on per-page display/terminal-predicate evidence, or require source-digest match before short-circuiting.
   **RESOLUTION: FIXED — commit `9baa8aa` (2026-09-05).** `resumeCompletedOutcome` gains a REQUIRED `allPagesDisplayCommitted` parameter (no default — every caller passes explicit evidence); the shell computes it via `activeRunPagesDisplayCommitted` (display evidence = manifest committed bundle OR durable textless terminal). TreatAsFinished fires only with full evidence; otherwise `null` dispatches to the legacy schedule, which re-derives the missing display while the COMPLETE sidecar stays untouched (FF-01c). Pinned at dispatch level by `BatchDispatchResumeWiringTest` Case 3 (RED verified pre-fix — TreatAsFinished short-circuit; GREEN post-fix — legacy starts, record byte-untouched).

5. **F-5 LOW — `boundPageKey` is read at async hydrate time, not captured at bind time.**
   `ui/reader/viewer/TranslationOverlayView.kt:109-113` — a rebind between bind and background hydrate execution can resolve the new page's plan against the old blocks. Bounded: `PersistedLayoutHydrator` re-validates block content, dimensions, and compatibility fingerprint per plan block (`PersistedLayoutHydrator.kt:92-142`), so a wrong-page plan nearly always returns non-Resolved → planner fallback; only FF-02-ON affected. Capture the key with the bind parameters.

6. **F-6 LOW — finalize retention reconciliation runs outside `NonCancellable`.**
   `ChapterProfileBatchCoordinator.kt` (`runFinalizeAndComplete` step 5): `store.flush()` is wrapped `NonCancellable` but `store.reconcileArtifactRetention()` follows outside it, whereas the cited legacy idiom (`BatchChapterTranslator.kt:781-795`) keeps retention inside. Cancellation there skips the GC sweep; safe (re-runnable) but diverges from the ST-14 idiom it cites.

7. **F-7 LOW — observability nits.** `OverlapScheduler.progressedInWindow` is written but never read (dead); `inpaintOne`'s non-committed branch increments `overlapInpaintFailures` even on the serial arm, mildly skewing gate-6.5 keep-or-revert evidence.
