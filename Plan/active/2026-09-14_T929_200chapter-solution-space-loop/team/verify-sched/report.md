## 2. Attack 1 — the 210s attach-starvation derivation (e.b#1)

**Verdict: OVERSTATED as written. The starvation window is a narrow per-page race, not "the entire preflight phase is effectively dead."**

The report treats the batch lease as held from OCR through the translate phase. It is not:

1. The preflight releases each page's lease strictly after its checkpoint: `ChapterProfileBatchCoordinator.kt:505-524` (`finally { … releaseBatchLease(pageKey) }`, `:522`).
2. The translate tail re-acquires a FRESH per-page lease at the Translation stage and releases it in `finally`: `BatchChapterTranslator.kt:650-660` (explicit ADAPTATION note: "the flagged preflight releases each page's lease strictly after its checkpoint… the wrapper therefore acquires a fresh BATCH page lease"), `:666-670`, `:722-724`. The AI lane does the same (`ProfileEnvelopeExecutor.kt:305`).
3. Therefore, at any moment during preflight, exactly ZERO or ONE page is batch-leased (the one in its OCR native turn). A manual tap on any other page is GRANTED the lease at `TranslationPipeline.kt:802` and runs its own single-page boundary immediately — the reader is unblocked in seconds-to-~90s+network, subject only to the native lane (V2: ~one batch job) and the governor (V4).
4. Attach (tap landing during that page's own OCR turn) resolves mid-tail, not only at chapter end: the tail commits each page's translation durably as it completes (`BatchLaneWorkers.kt:1060-1079`; textless `:888-906`), and the attach predicate fires on the store StateFlow per page (`TranslationPipeline.kt:745-764`). So the wait is (remainder of the chapter's OCR) + (tail pages preceding the tapped page), which for a 15-page standard-lane chapter at ≥4s pacing is typically well under 210s; it can exceed 210s for late pages on slow providers or in the AI lane (analysis + envelope phase), but that is a tail case, not the whole preflight.

**Counter-finding the report missed (HIGH, batch stall):** the tap that wins the lease during preflight makes the batch DEFER that page (`BatchLaneWorkers.kt:329-341`) → no checkpoint for it → `corpusGaps > 0` → `corpusFingerprint == null` → run returns **PAUSED** at `ChapterProfileBatchCoordinator.kt:556-569` — before the branch, so BOTH lanes stall, and there is no in-pass rescan (V12). Only if the manual finishes and releases before the loop reaches the page does the batch reuse it via SKIP_ALL and checkpoint it (`BatchLaneWorkers.kt:360-393`). The same gap arises from a `LowMemoryDecodeDeferredException` during preflight (`BatchLaneWorkers.kt:429-447` writes FAILED, no checkpoint). For the 200-chapter baseline (scenario C: reader reads while batch runs), this manual-tap-pauses-chapter interaction is at least as reader- and throughput-relevant as the 210s attach, and it is absent from the report.

## 3. Attack 2 — FCFS on the native mutex

**Verdict: AGREE, mechanism corrected.**

- kotlinx `Mutex` is fair (FIFO by suspension); no priority, no queue-jumping. `tryRunExclusive` (`NativeRunQuarantine.kt:51-59`) succeeds only when the lock is free — teardown cannot preempt a queued invocation.
- The only lever that resembles priority is incidental: `yield()` between batch pages (`ChapterProfileBatchCoordinator.kt:381-383`) lets an ALREADY-QUEUED manual waiter take the lane before the next batch page. It does nothing for a manual that arrives mid-invocation.
- Correction (already in V2): because the batch OCR loop is serial, a manual arrival queues behind only the CURRENT invocation (≤120s cap) and any already-queued overlap-window inpaint — not "every queued batch native job" (A.1) nor "many page-OCR durations" (e.b#2). The real reader pain during preflight is therefore the lease/attach path (§2), not native-queue depth.

## 4. Missed dead-time sources

1. **Corpus-gap PAUSE (HIGH)** — see §2; costs the whole chapter's remaining schedule and needs a re-queue to resume (checkpoints make the retry cheap).
2. **Provider connection setup**: first request to a host pays DNS+TCP+TLS on a possibly cold OkHttp pool — absent from e.a/e.c.
3. **Adaptive envelope retries**: `translateAiChunkWithAdaptiveRetry` (`ProfileEnvelopeExecutor.kt:560-575`) re-enters the 15-RPM sublimit per attempt; retry latency under quota is not in e.c#8.
4. **15s foreground-wait deferral**: a manual waiter that cannot be admitted within `maxForegroundWaitMs` is DEFERRED (`ProviderRequestGovernor.kt:484-503`, `:356-362` throws typed Paused) — the reader sees a Paused/retry cycle, a latency mode missing from e.a/e.b tables (which only count waiting, not deferral).
5. **Sublimit burst tails**: after a 15-burst, `nextEligibleAt` can push ~60s out (`:516-518`); "≥4s average" understates worst-case per-envelope pacing.
6. **Memory-gate deferral → PAUSE**: decode-defer during preflight leaves no checkpoint (see §2) — the retry is not free; it costs a full run restart (cheap via checkpoints, but a stall).
7. **Envelope payload build**: `buildEnvelopeChunk` + glossary prefix token estimation (`ProfileEnvelopeExecutor.kt:872-897`) is heap/CPU work before every dispatch; minor but serial in the one-in-flight lane.

## Bottom line

The report's resource map is accurate and well-cited (V1, V3–V11 all confirmed). Two material errors: (1) e.b#1's 210s starvation is derived from a lease model the code contradicts — the batch releases per-page leases after OCR and re-acquires per translate, so the starvation window is a narrow tap-during-own-OCR-turn race, while the REAL preflight hazard is the opposite one (a manual tap or decode-defer creates a corpus gap that PAUSES the whole run, with no in-pass rescan); (2) native-lane wait depth for manual is ~one batch invocation, not the queued-preflight chain. F.1/F.2/F.5 and the core no-gos stand; F.1 needs the corpus-gate/resume rework in its risk register, and F.4's fourth bullet needs rephrasing.
