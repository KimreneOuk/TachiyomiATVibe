# T924 architecture overview — independent edge review

Date: 2026-09-05. HEAD: `adbe643`. Architecture discussion only; no implementation or runtime tests. Read reviewer role, T924 contract/design/reverification and T923 source investigation. Citations below are relative to `app/src/main/java/eu/kanade/translation/`.

## Executive findings

The existing code already has stage-aware reuse, shared origin leases, sequential AI envelope coordination, durable pause/failure handling, and a rolling context frontier. Proposed Fast/Efficient modes and 15-RPM default must be labelled proposed, not existing. Avoid promising zero duplicate paid calls, universal fingerprint safety, instant first results, or a 48-MB total process ceiling.

## Verified user journey nuances

1. **VERIFIED — fragmented progress is stage-based, not last-read based.** Batch hashes all ordered source streams before planning (`pipeline/batch/BatchChapterTranslator.kt:384-409`); planner inputs include current source and stage fingerprints and AI glossary version (`pipeline/batch/BatchResumePlanner.kt:91-108`). Tracker rebuild reads store state (`pipeline/batch/TranslationBatchProgressTracker.kt:52-76`). In the example 1/2/4 complete, 3/5/6 missing, valid completed pages are candidates for retention; only unfinished stages need work. This is conditional on compatibility, not simply a translated boolean.
2. **VERIFIED — actual fragment retention has an extra live gate.** Chapter planning rewrites later REUSE to WAIT_FOR_DEPENDENCY after the first unresolved translation (`model/PageWorkPlanner.kt:114-149`). AI worker recognizes later READY/SKIPPED pages with matching translation fingerprint and skips their provider call (`pipeline/batch/BatchLaneWorkers.kt:1318-1355`). It records these pages for context (`:1384-1390`). Frontier retains completed pages after a gap and folds them only once predecessors complete (`pipeline/batch/BatchContextFrontier.kt:51-84`). Page 4 never enters the preceding-page rolling history for page 3; when page 3 completes, already-recorded page 4 can advance the frontier. Pages 3/5/6 can share an envelope; this does not imply three calls. The chapter glossary is separately seeded from historical translated pairs, so do not claim later-page information can never appear anywhere in a request.
3. **VERIFIED — completed does not mean permanently exempt.** Source/config changes or missing physical cleaned files cause stage-specific replanning (`pipeline/batch/BatchResumePlanner.kt:91-108,228-255`). AI glossary maturation can deliberately schedule translation repair (`model/PageWorkPlanner.kt:290-309`). Promise preservation of valid compatible work, not all prior translations regardless of settings.
4. **VERIFIED — partial responses stop progression.** A page remaining PARTIAL after adaptive translation is persisted as a retryable partial candidate and returns Paused; completed preceding pages are retained (`pipeline/batch/BatchLaneWorkers.kt:535-563,584-619`). PARTIAL does not advance rolling context (`pipeline/batch/BatchContextFrontier.kt:56-66`). Refusal and validation failure have terminal outcomes (`BatchLaneWorkers.kt:511-532,565-581`). Current chunk processing stops the outer pass when its result is not Completed (`pipeline/batch/SequentialBatchCoordinator.kt:688-695`).

## 15 RPM proposal and efficiency

**VERIFIED:** Current cloud policy is 60 RPM, 60,000 estimated TPM, 1-second spacing and one in-flight request per bucket (`translator/ProviderRequestGovernor.kt:66-84,655-665`). Shared instance covers batch, reader, auto and settings (`:668-673`). Gemini bucket identity includes backend/model/hashed credential and obtains current request priority (`translator/providers/GeminiTranslator.kt:166-181`). Each HTTP attempt goes through governor; retries can make one semantic envelope cost more than one request (`ProviderRequestGovernor.kt:343-394`).

**Architectural recommendation:** Make 15 RPM a shared default for each applicable cloud quota bucket, while keeping interactive priority, provider cooldowns and token accounting. Otherwise a separate batch limiter could allow reader calls to push total traffic beyond 15. The current policy callback accepts only the key, not origin (`ProviderRequestGovernor.kt:247,292`): changing its default is shared behavior, not a batch-only preference. If a strictly batch-only cap is required, it is an additional allowance beneath the shared quota, not another independent provider bucket. This is design clarification, not an implemented change.

The existing limiter is a rolling window. A 15-RPM ceiling does not require an unconditional four-second sleep after each request. Interactive waiting reserves one request slot and 20% token headroom only while an interactive waiter exists (`:443-468`); it does not preempt an admitted batch request or guarantee instant reader admission.

**Quality trade-off:** Envelope attachment drops glossary first, then rolling context when budgets require (`translator/contextual/TranslationContextChunkPlanner.kt:92-120`). Fewer requests do not by themselves prove better quality. Cap numbers, minimum fill and an optional first-envelope exception remain tuning candidates. The Director's clarified objective supports efficiency-oriented default with optional earlier feedback; neither Fast nor Efficient is an implemented selector in this design. Preserve token backstop and pre-check probe contract and ship scheduling changes with chunk-boundary coverage.
