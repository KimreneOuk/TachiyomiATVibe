# Final adversarial review — T933 proposal

Reviewed `report/DIRECTOR_PROPOSAL.md` as of 2026-09-14. Verdict: **approve the architectural direction for discussion; not implementation-ready**. The proposal addresses preliminary R1–R6, R8–R9 and correctly separates tokenizer planning from actual-model fit. Three specifications need tightening before claiming a complete implementation contract. No production/test edits or tests executed.

1. **HIGH / plausible / design gap — durable request reconstruction is underspecified.** Proposal `:16`, `:54`, `:66` promises exact retry/resume snapshots, but only explicitly stores their fingerprint with page/envelope provenance; the chapter sidecar at `:52` stores contribution digests and metadata, not request text. A digest cannot reconstruct a deleted/replaced predecessor translation after a concurrent manual commit or process death. Existing profile snapshots are immutable (`app/src/main/java/eu/kanade/translation/artifact/ChapterTranslationProfile.kt:235–248`, `:259–260`), and freeze supersession keeps old bytes (`app/src/test/java/eu/kanade/translation/pipeline/batch/ProfileFreezePublicationTest.kt:153`). Require immutable bounded request-context sidecars, or retained immutable contribution generations plus complete deterministic selector/prompt version inputs, durably referenced before D9 dispatch. Explicitly say Increment 1 keeps current resume guarantees and does not yet provide this new durable replay guarantee. Confirm with crash after ledger publication before response and predecessor replacement while a request is retained; resumed context bytes must match, or the run must fail closed with an explicit new-generation policy.

2. **MEDIUM / likely / design gap — aggregate memory bound is not yet explicit.** Proposal `:58` bounds one serialized request but does not bound bytes of the live projection, frozen base, ranking/contribution index, simultaneously decoded sidecars, or temporary serialization/reconciliation allocations. Incremental ranking may still retain all candidates (`app/src/main/java/eu/kanade/translation/translator/contextual/ChapterGlossaryBuilder.kt:59–75`); reconciliation currently materializes all durable chunks (`app/src/main/java/eu/kanade/translation/pipeline/batch/ChapterProfileBatchCoordinator.kt:999–1042`). Require an explicit total resident budget with category accounting and disk-backed/streamed fallback. UTF-8 serialized bytes are not Kotlin/Java heap bytes. Until measured/derived, label the current numbers a request-payload cap, not the total memory contract. Confirm with high-distinctness 200-page data and peak heap/work instrumentation.

3. **LOW / certain / editorial contradiction — Increment 1 independence versus rollout dependency.** Proposal `:50` says Increment 1 has no T930 dependency; `:76` places it after T930 Slice A/B. State whether this is a deliberate scheduling preference or allow Increment 1 after the shared allocator gates independent of T930 approval. Do not accidentally make the read-only projection blocked on an unapproved durability program.

Additional precision: proposal `:66` must mean an unchanged publication of the same policy semantics when saying policy publication does not replay analysis; changed analysis policy/input compatibility can legitimately require replanning (coordinator validates persisted prefix against the current plan at `app/src/main/java/eu/kanade/translation/pipeline/batch/ChapterProfileBatchCoordinator.kt:696–698`). No need to replay analysis for unrelated rolling changes.

Safety-net preservation, output non-authority, field-specific conflicts, frozen/live separation, rescan limitation and honest O(B) correction are accepted. No remaining objection to one service/document owning multiple typed producers, provided the above details are carried into the implementation contract.
