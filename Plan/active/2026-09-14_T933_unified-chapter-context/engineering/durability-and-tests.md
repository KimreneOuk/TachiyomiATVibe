# Unified context durability and test boundaries

Design proposal only, 2026-09-14, investigated against HEAD 9c19ad0. No production/test edits or test execution. Paths below are repository-relative. Prefix `main/` means `app/src/main/java/eu/kanade/translation/`; `test/` means `app/src/test/java/eu/kanade/translation/`.

## Recommendation

Use one chapter-context facade with immutable request snapshots and typed producers. Keep the existing glossary compatibility version, frozen-profile input/content identities, and run/write fencing as distinct fields. A single revision is useful for observing publication order but is insufficient as the reuse key. Introduce durable context pointers only with the approved T930 transaction work; first ship a shared read-only projection over existing stores and leave all existing safety assertions unchanged.

## Proposed schema and identities

PROPOSAL: introduce `ChapterContextSnapshot` schema 1 behind the facade. Store no bitmap or full chapter transcript in it. Fields:

- `schemaVersion`, `kind`, `chapterKey`, source/target language, `contentFingerprint`.
- Typed producer references: glossary pointer plus semantic fingerprint; optional frozen profile pointer plus profile-input identity; user-authority reference; committed rolling-context page references containing page key, generation, source identity and selected-pair digest. Missing producers are explicit absence, not empty-string hashes.
- Bounded facts/hints with stable IDs, source evidence references, scope/range, producer identity, confidence/conflict state. Model-produced target strings remain vocabulary/continuity hints. They cannot establish speaker, gender or relationship facts without source evidence.
- `selectionPolicyVersion`, `serializationPolicyVersion`, and `sourceCoverage` including known natural-order coverage. The snapshot has no mutable latest-version lookup.

PROPOSAL: distinguish three identities:

1. `chapterContextRevision`: durable publication ordering/diagnostics only; advances on effective committed context change; an equal-map or semantically equal update is a no-op.
2. `requestContextFingerprint`: canonical identity of the exact selected/truncated payload sent, including selected source/target pair digests, evidence references, producer semantic identities, language and selection/serialization policy. Exclude publication timestamp, run ID and chapter revision. Capture before provider dispatch; never rewrite this field after the response. Store it in the page/envelope result provenance.
3. `reuseCompatibility`: retain existing stage fingerprints, glossary compatibility version and profile identities, with an explicit future policy version if needed. Do not compare the request hash against the newest global context hash. The former records what was seen; the latter answers whether an existing artifact remains usable.

This prevents self-invalidation: page P uses snapshot S; accepted P contributes new hints yielding S2; P records S as request evidence and the existing post-fold glossary compatibility stamp for D5. A later unrelated rolling pair changes a request selection but does not itself demand a paid repair of P. Actual glossary maturation still repairs eligible earlier AI pages exactly as D5 requires. A future more selective repair policy is a separate product change, not an incidental consequence of introducing a facade.

PROPOSAL: the initial shared projection uses existing pointers and remains ephemeral. Durable phase adds `context: SidecarPointer?` to the manifest, a frozen context-base pointer/policy identity to run records, and a request-context provenance field to page snapshots/results. Bump the manifest schema before writing the new required pointer; retain reading of schemas 2/3. Keep older sidecar serializers/identities intact and introduce versioned new fingerprints rather than changing FP-04/05/06 in place. Old records with absent request-context identity remain unknown, not stale by default. New mandatory-context run shapes must be explicitly versioned; old frozen runs finish with their recorded compatibility behavior or pause with an honest incompatible-run reason. Never silently reinterpret an active frozen run using current settings.

UNKNOWN: exact rollout schema number and serializer compatibility require the integration branch at implementation time. This report proposes the next manifest version (currently 4); it does not authorize migration deletion.

## T930 integration and lifecycle

PROPOSAL, dependent on T930 approval and binding amendments A–H:

- One store mutex owns contribution replacement, snapshot selection and staged context changes. Capture an immutable snapshot under the mutex, release it before network work. Manual, auto and both batch shapes use this facade; standard engines receive empty unsupported context and keep byte-identical reuse decisions.
- Separate `durableManifest` from staged mutations structurally. Readers forming requests may use only committed context. A staged context delta is private transaction input, never a publishable manifest copy. The initial facade must not describe live glossary memory as durable truth when its publish failed.
- At page-terminal promotion, compute accepted contribution replacement, pending glossary compatibility version and context delta under the same owner. Publish all required immutable sidecars before the combined manifest containing page generation, glossary/context pointers and post-fold compatibility stamp. If publication fails, neither contribution nor compatibility version becomes committed. The exact pre-request snapshot remains unchanged.
- Pending-version stamping must use the allocated sidecar version, including orphan-induced gaps, not `durableVersion + 1` guessed independently. Preserve `updateGlossary(equalMap)` no-op. Contribution replacement must not accumulate duplicate/stale contributions on retry or retranslation.
- Existing glossary/legacy pointer APIs force-flush before publishing and rebuild only from fresh durable truth (amendment F). Do not pass a staged manifest to their current nontransactional `publishManifest`. New context publication should use the same transactional facade as other sidecars.
- Registry is observability-only flag OFF. Flag ON, second writers request owner flush, then reread durable truth; retain disk CAS and add bounded stale retry defense. Fresh future-schema guards remain uncached. A context writer is another registered writer, never an exception.
- OCR checkpoint CLOSE, chapter phase records, page-terminal promotion, chapter COMPLETE, explicit fenced flush, and bounded STOP drain are commit boundaries. Context-only evolution can share an already-required boundary; do not publish each token or block.
- D9 attempt ledger remains immediately durable before the paid call and is never staged. The request snapshot is frozen before that entry/call; no accepted context contribution exists until result commit.
- Crash before publication drops staged contributions and page mutations. Crash after sidecar but before manifest leaves only collectible orphans. Crash after manifest reconstructs matching page/context/glossary state. Resume adopts durable OCR and frozen context-base identities; do not replay analysis merely because a run ID, timestamp or envelope policy changed.
- Orderly eviction/close drains at the existing bounded seam; closeAndFlush remains sweep-free. Engine-epoch stop follows D7. Grace expiry commits nothing and leaves the D9 entry unresolved. Defunct work is dropped/joined within the existing timeout, never resurrected by a late context publication.
- Retention must include durable and staged pointer roots, active request pins and frozen run references, plus retained page generations. Avoid recursively loading all context snapshots per commit. Keep an explicit bounded reference index and collect obsolete snapshots at the existing retention triggers.

PROPOSAL memory limits: one in-flight request snapshot per execution owner, one current chapter projection plus frozen active-run base; rolling selection bounded by both tokens and page count. Snapshot payload proposed ceiling 64 KiB UTF-8 plus bounded metadata; at most 64 selected fact records with existing bounded fact fields. This is separate from the 8192-token request allocator and must not be advertised as an 8192-token guarantee. Keep per-page contribution bookkeeping O(pages + retained term occurrences), replace on retranslation, and measure its bound on 200 dense pages. Full chapter-profile facts can stay on disk and be selected into the bounded request; no 200-page bitmap retention is introduced.
