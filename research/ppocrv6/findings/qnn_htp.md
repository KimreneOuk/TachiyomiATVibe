# PP-OCRv6 QNN HTP compatibility

Status: offline inventory only. No Qualcomm QAIRT/QNN SDK, Android device, `adb`, QNN tool, or QNN-enabled ONNX Runtime provider was available in this worktree. The machine has Python 3.11, `onnx` 1.20.1, and CPU/Azure-only `onnxruntime` 1.24.1. Therefore every HTP conclusion below is `UNTESTED` rather than a device failure.

The raw, reproducible graph inventory is [`research/qnn_compatibility_raw.json`](../qnn_compatibility_raw.json), generated by [`research/inspect_qnn_compatibility.py`](../inspect_qnn_compatibility.py). It includes SHA-256, ONNX opsets, all graph I/O shapes, every node/attribute, quantization-node counts, unknown-op inventory, and local tooling evidence.

A fresh direct `onnx.ModelProto` read and this inspector agree on DET 14 and REC 11; the hashes and byte sizes match the repository's graph-analysis artifact. No generated PP-OCRv6 variant is used by this report.

## Graph evidence

### DET

* Input `x`: `FLOAT [DynamicDimension.0, 3, DynamicDimension.1, DynamicDimension.2]`.
* Output `fetch_name_0`: `FLOAT [ConvTranspose_459_o0__d0, 1, ConvTranspose_459_o0__d2, ConvTranspose_459_o0__d3]`.
* 83 `Conv`, 2 `ConvTranspose`, 13 `Erf`, 13 `HardSigmoid`, 6 `Resize` plus arithmetic/pooling/activation nodes.
* ONNX opset 14 (IR 10); graph input and output dimensions are symbolic.
* No `QuantizeLinear`, `DequantizeLinear`, or quantization annotations. The graph input and all observed activations are FLOAT.
* The model's `inference.yml` documents TensorRT dynamic profiles `1x3x32x32` (min), `1x3x736x736` (opt), and `1x3x4000x4000` (max). These are TensorRT profiles, not proof that QNN accepts dynamic shapes. The validation script uses fixed `1x3x32x32`, `1x3x640x640`, and `1x3x736x736` probes; `4000x4000` is intentionally omitted because of memory risk.

### REC

* Input `x`: `FLOAT [DynamicDimension.0, 3, 48, DynamicDimension.1]`.
* Output `fetch_name_0`: `FLOAT [DynamicDimension.0, Reshape_471_o0__d2, 18710]`.
* 57 `Conv`, 13 `Erf`, 5 `HardSigmoid`, 3 `Softmax`, 3 `BatchNormalization`, and other arithmetic/reshape nodes.
* ONNX opset 11 (IR 6); batch and width are symbolic while height is fixed at 48.
* No `QuantizeLinear`, `DequantizeLinear`, or quantization annotations. The graph input and all observed activations are FLOAT.
* The `inference.yml` TensorRT dynamic profiles are `1x3x48x160` (min), `1x3x48x320` (opt), and `8x3x48x3200` (max). The validation script probes fixed `b1/w160`, `b1/w320`, `b1/w3200`, `b8/w320`, and `b8/w3200`; this explicitly covers dynamic batch and dynamic width.

### Variants searched

The asset tree contains only the two PP-OCRv6 FP32 ONNX files above. No PP-OCRv6 FP16, INT8, or QDQ DET/REC variant exists. Other asset models include unrelated INT8/QDQ graphs, but they are not PP-OCRv6 and are not evidence that these OCR graphs are QNN-ready.

## QNN/HTP implications

The [ONNX Runtime QNN Execution Provider documentation](https://onnxruntime.ai/docs/execution-providers/QNN-ExecutionProvider.html) states that QNN EP does not support dynamic shapes and that the HTP backend normally requires quantized models. Its public operator inventory does not list `Erf` or `HardSigmoid`; it does list `Gelu`, but these graphs contain explicit `Erf` subgraphs rather than a `Gelu` node. QNN/ORT graph transformers may fuse some patterns (and QNN source has Hardsigmoid-related fusion code), but that is version-, pattern-, dtype-, and backend-dependent. Treat these nodes as a partition risk until a no-fallback device session succeeds.

Expected partition behavior for the current assets is therefore:

1. Dynamic shapes can prevent QNN graph construction before useful partitioning; fix every input dimension first.
2. A fixed FP32 model is still not an HTP deliverable under the documented HTP workflow. Quantize with representative OCR calibration data to QDQ, usually using QNN's supported unsigned activation/weight combinations.
3. After QDQ conversion, `Erf`/`HardSigmoid` (or their fused replacements), resize attributes, convolution layouts, and output dequantization must be tested. Unsupported nodes may fall back to CPU unless fallback is disabled.
4. Use `session.disable_cpu_ep_fallback=1`; a successful run then proves that ORT did not silently execute an unsupported subgraph on CPU. Enable detailed profiling to record HTP execution and latency.

QNN context binaries are useful after a graph is proven: the ORT docs describe `ep.context_enable`, `ep.context_file_path`, and `ep.context_embed_mode`, and require the context to be regenerated when the model, QNN/ORT build, SoC, HTP architecture, or relevant provider options change. Context caching is an optimization, not compatibility evidence.

## Android validation procedure

[`research/validate_qnn_android.sh`](../validate_qnn_android.sh) performs the fixed-shape rewrites, stages standard `onnx_test_runner` fixture directories, pushes the Android runner/models/QAIRT libraries, and prints exact no-fallback commands. It is dry-run by default. It does not invent random OCR inputs.

Host setup (on a Linux/macOS shell or Git Bash):

```sh
export ORT_TEST_RUNNER=/absolute/path/to/android/onnx_test_runner
export QNN_LIB_DIR=/absolute/path/to/qairt/2.xx.x/lib/aarch64-android
export DEVICE_SERIAL=<adb-serial>       # optional
bash research/validate_qnn_android.sh
```

Populate each generated `research/qnn_android_validation/fixtures/<case>/test_data_set_0/` with representative `input_*.pb` tensors matching the fixed shape. Then run:

```sh
RUN=1 bash research/validate_qnn_android.sh
```

The runner invocation is equivalent to:

```sh
adb shell /data/local/tmp/ppocr-qnn/bin/onnx_test_runner \
  -e qnn \
  -n det_b1_640x640 \
  -C 'session.disable_cpu_ep_fallback|1' \
  -i 'backend_path|/data/local/tmp/ppocr-qnn/libQnnHtp.so profiling_level|detailed profiling_file_path|/data/local/tmp/ppocr-qnn/det_b1_640x640.csv' \
  /data/local/tmp/ppocr-qnn/fixtures
```

Repeat for every DET/REC shape emitted by the script. Record model-load errors separately from runtime output mismatch, and record invalid provider/configuration errors separately from model incompatibility (for example, missing `libQnnHtp.so`, wrong ABI, wrong SoC/HTP arch, missing RPC libraries, or a malformed `-C`/`-i` argument are environment/configuration failures).

For a proven QDQ model, rerun with the same shapes and no-fallback setting, then add context generation (`ep.context_enable=1`, optionally `ep.context_embed_mode=1`) and rerun from the context model. Do not cache a context from a different QAIRT/ORT/SoC/HTP configuration.

## Bottom line

Do not route the current PP-OCRv6 DET or REC files to QNN HTP. First create fixed-shape QDQ variants (keeping CPU/NNAPI fallback for normal operation), then validate every intended fixed shape on a Qualcomm Android device with fallback disabled. The present repository evidence supports **UNSUPPORTED / UNTESTED** for both current graphs and **DEVICE TEST / UNTESTED** only for future quantized variants.
