## 1. Findings

### F-W6-1 — LOW (transient BATCH lease hold on the TX-21 drift / lost-page early-return paths; self-healing, teardown-bounded)

`ProfileEnvelopeExecutor.dispatchEnvelope` acquires the page's BATCH Translation lease (`ProfileEnvelopeExecutor.kt:277`) before revalidation. The `pageAuthoritativelyDone` skip (`:300-302`) and the empty-dispatch-blocks skip (`:319-321`) release explicitly; pages added to `held` are released in the `finally` (`:468-473`). But the two early-return error paths — `live == null` (`:295-297`) and `revalidationDrift != null` (`:305-311`) — return `ReplanNeeded` WITHOUT releasing the current page's just-acquired lease (that page is not yet in `held`). Consequences verified:

- Not a correctness hole: `PageStageLeaseTable.tryAcquirePageStageLease` (`store/PageStageLeaseTable.kt:75-116`) returns the SAME token for a same-origin re-acquire, so the re-planned re-dispatch of that page re-acquires idempotently and the lease is released at that envelope's `finally`.
- The hold is bounded by pass teardown: `BatchChapterTranslator` releases all BATCH leases after the pass (`releaseAllPageLeases(PageWriteOrigin.BATCH)`, verified at `BatchChapterTranslator.kt:763` in the OOM branch and in the shared teardown the ST-14 contract cites at :767/:780 — the profile-pipeline coordinator runs inside the same `runPass1` generation wrapper).
- Residual exposure: between the drift return and the re-dispatch (or after a terminal pause such as `MAX_CONSECUTIVE_REPLANS` / `ReplanResult.Failed` / `Drained` via replan-`NothingPending`), the page is BATCH-locked at the Translation stage; a MANUAL reader translation attempt on that one page is Denied in that window (MANUAL-vs-BATCH is never a preemption, lease table :87-98).

Fix direction: in the `live == null` and drift early returns, `store.releasePageStageLease(pageKey, BATCH)` before returning (mirroring the two skip paths), or add the page to `held` before returning so the `finally` covers it. One-line each; can ride any later slice-A touch. Not blocking: pipeline behavior, durability, and resume are unaffected.

### F-W6-2 — LOW (coordinator-level ST-11 plan-reuse branch untested)

The ST-11 resume rule "identical inputs reuse the published plan, no write" is implemented (`ChapterProfileBatchCoordinator.kt`, `runEnvelopePlanAndTranslate` Ready branch: `manifest.envelopePlan != null && readValidatedPlan(...).planFingerprint == fresh.planFingerprint` → skip publication) — but no test drives it at coordinator level: the full-dispatch test is a single run; the resume test legitimately produces a DIFFERENT fingerprint (8 pages committed → suffix re-plan → supersede); the no-work resume exits at `NothingPending` before the Ready branch. Only publication-level idempotence is pinned (`EnvelopePlanPublicationTest` "byte-identical republication is idempotent at the same content address"). Risk is minimal because the fallthrough is safe by construction — a falsely-negative reuse check triggers a publication that is content-address-idempotent — but the branch that AVOIDS a manifest write on every no-drift resume is exactly the ST-11 resume guarantee and deserves a pin.

Fix direction: coordinator test — run 1 completes envelopes (translator wired); run 2 with unchanged state reuses: assert `publishSidecarPointers` not re-invoked (recording store or pointer file mtime/inode unchanged) and the run still drains.

### F-W6-3 — NOTE (store partial-block apply semantics vs page atomicity — pre-existing, unreachable-in-practice here; record for Stage 7)

The report claims "a partially-covered page commits NOTHING (page atomicity)". At the executor level this holds by construction: `fullyCovered` requires EVERY dispatchable block id present in `outcome.blockTranslations` (`ProfileEnvelopeExecutor.kt:391-393`), `commitPages` patches only fully-covered pages, and extra/invented response ids are ignored (patches keyed by planned ids only). At the STORE level, however, `mergeTranslationLocked` applies per-block and commits the page when `applied.isNotEmpty()` even if some blocks were rejected (`ChapterTranslationStore.kt:1177-1204`) — a patch with one stale block and three fresh blocks would commit the three with `translationStatus = READY`. For this slice the hole is unreachable: the full M4 ladder (`generation/pageVersion/leaseToken/candidate/dependency/artifactPageVersion`, :1151-1160) rejects the WHOLE patch before the block loop for every realistic mid-flight mutation (any OCR rewrite or user edit bumps `pageVersion`/lease), and the executor pauses on ANY `Rejected`. Not a regression of this commit (pre-existing semantics, first exercised by this slice). Flag for Stage 7 (layout commits) where per-block CAS + page atomicity interact again: consider a store-level strict mode (reject if `rejectedTargets.isNotEmpty()`).

### F-W6-4 — LOW (carried ledger item, re-confirmed on new code): DR-D bucket key spelling split for LM Studio

`buildEnvelopeDispatchWork` derives the sublimit bucket identity from `frozenConfig.providerKey.substringBefore(':')` (`ChapterProfileBatchCoordinator.kt`, work builder tail) — yielding `lmstudio` (wave-4's noted enum spelling) while the governor backends use `lm_studio`. For an LM Studio credential the translation-envelope Batch bucket and any other Batch bucket keyed with the governor spelling would form two independent 15-RPM pools — the exact DR-C violation shape ("one allowance per credential for all Batch traffic") for that backend. Masked today: no production transport (translator seam null = CONFIGURATION gate), and the test wiring uses `fake:provider` consistently. Already owed in the wave-5 ledger ("`lmstudio` vs `lm_studio` spelling alignment" as a provider-package acceptance condition); this slice ADDS a second spelling site that the alignment must cover. Fix direction: single shared mapping helper for providerKey-part ↔ governor backend, or key the Batch bucket on the raw credential scope only (backend-agnostic), with a pin test.
