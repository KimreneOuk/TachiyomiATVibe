## Ranked wins (win / complexity; correctness constraints stated)

- **W1 — Visible-first page hydration at store open** (win: High for large translated chapters / complexity: High, correctness-sensitive). The eager O(pages) snapshot read at :4901-4913 is the core open cost; the reader only needs the visible/warm window at M2/M3. Direction: open by hydrating journal outcome metadata + manifest records only, synthesize placeholders (`toArtifactPageFallback`) for unread keys, and hydrate real content on first display touch. **The existing `getOrLoadPageSnapshot` is NOT reusable unchanged for this** (ChapterTranslationStore.kt:4398-4431): it selects the candidate snapshot name BEFORE the committed one (:4405), loads WITHOUT the open-time expected-fingerprint verification (:4409 vs `readVerifiedSnapshot` :4895-4899), and promotes the loaded snapshot to committedDisplay whenever any committed pointer exists (:4414) — under visible-only hydration, where candidate and committed can differ, that can publish candidate bytes under a committed authority. A lazy hydration path must add explicit candidate/committed selection + fingerprint verification and check ACK/journal/tombstone authority (blockedManifestKeys/outcomes :4914-4955) BEFORE promotion. Must also preserve: journal authority gating for unread keys; fingerprint verification at per-page read time; and placeholders that never fake READY for status/planner consumers (manifest committed records remain the payload-validity signal, matching `stageEvidence` fallbacks in PageWorkPlanner.kt:416-487). Sequence first behind ReaderEntryTrace data; do not attempt without the W5 traces.
- **W2 — Cheap status resolution without a full open (HTTP/local)** (win: Medium / complexity: Medium). `artifactStatus()` needs hydrated page state today (StoreStatusProjector.kt:91-139 uses `inputs.state`/`display`), so the cold status path pays a full open. A manifest/journal-metadata-only status projection (committed-run evidence rule already exists for artifact-only stores :96-97) would let `persistedChapterStatus` answer without the probe open; the active open then happens once, on demand. Risk: status derived without journal replay can disagree with the post-open status — keep the existing invalidation protocol (`clearDurableStatusCache`) and prefer the active-store truth once open.
- **W3 — Bounded parallel per-page snapshot reads** (**EXPERIMENT, not a proven win)** (win: plausible, scales with page count — UNPROVEN / complexity: Low-Medium). The loop at ChapterTranslationStore.kt:4901-4913 issues independent SAF reads + hashes sequentially inside `withContext(Dispatchers.IO)` (:4806). A bounded-concurrency map would keep per-page verification and merge order identical, but this is an EXPERIMENT: throughput is not proven faster (SAF/binder may serialize server-side), and the store mutex, IO dispatcher saturation, and binder concurrency limits must be validated (page-snapshot reads at :4901 run BEFORE the store exists, but the fingerprint hashing and downstream merges still need a concurrency-safety review). Validate behind W5 traces before keeping.
- **W4 — Promote the status probe store instead of close-then-reopen (HTTP/local)** (win: Medium, removes a duplicate full open / complexity: Medium). `withProbeStore` releases owned probes after the status read (:224-231); the immediately following active open redoes the same work. Promoting the probe into the chapterId slot under `withChapterStoreAdmissionLock` avoids the second open; ownership/lazy-persistence flags and the probe-registry release protocol need care. Alternative (smaller): `getChapterTranslationForReader` and the status path already share the registry — ensure the reader's `openOrCreateActive...` runs BEFORE the status read on non-download paths (call-order change in `loadChapter`) so the status fast path hits.
- **W5 — Trace the open internals** (win: enables all above / complexity: Low). `ReaderEntryTrace` covers manifest/recovery/retention stages (ChapterArtifactEngine.kt:110-159) and `download.getPages` already breaks out findDir/translation/buildList/mapping nanos (DownloadPageLoader.kt:107-115), but journal replay and the per-page snapshot loop have NO spans. Add `store.journalReplay` and `store.pageSnapshotHydration` (count + bytes) so W1/W3 are data-driven before any change.
- **No change recommended**: chapter-switch teardown is prompt in the stated scenario (no active translation); the 210 s drain bound only bites with an in-flight paid call, and bounding that join risks stranding attempt-ledger entries — leave as-is, monitor via the existing `still-running` watchdog (ReaderEntryTrace.kt:17-30).

## Notes

- The status/document caches (DurableChapterStatusResolver.kt:61-64) and the active-store registry already prevent repeat work within a session; consecutive chapter switches pay one active open per new chapter (status is a cache/registry hit), not the cold-entry cost.
- In-code historical figures quoted (60-210 ms per SAF walk; 5-9 s for a 68-page status probe) are PRIOR-fix comments in the source (DurableChapterStatusResolver.kt:134-136, ReaderViewModel.kt:912-917), not measurements from this round.
